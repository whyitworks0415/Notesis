# Notesis 0.99.7 (248)

<!-- update: manual -->

> 수동 업데이트입니다. 앱이 먼저 알리지 않으며, **About · Help → Check for updates**에서 설치할 수 있습니다.

> ⚠️ 0.91.0부터 앱은 **Material 화면만** 씁니다. Liquid glass·Glassmorphism을 계속 쓰려면 0.90.28에 머무르세요.

0.99.6(타일을 백그라운드에서 칠하기)에 이어서, 렌더링 플랜의 나머지 B·C·D·F를 넣었습니다.

## 바뀐 점

### B. 실제 렌더 시간을 보고 GPU 작업량을 자동 조절
- 매 프레임 Android가 알려 주는 실제 시간(UI 스레드, 스레드 간 동기화, RenderThread, GPU)을 읽습니다.
- 동기화+RenderThread+GPU가 한 프레임 시간을 넘으면, 다음 프레임의 "GPU로 새로 칠할 획 수"를 **절반으로** 줄입니다(최소 10%까지). 제때 끝난 프레임마다 10%씩 되돌립니다.
- 지금까지는 미리 정한 시간 예산만 썼고, 그 예산은 RenderThread가 얼마나 밀렸는지를 몰랐습니다.

### D. RenderThread가 밀리면 작업 스레드가 양보
- RenderThread가 프레임을 넘긴 직후(0.3초 동안)에는 두 가지를 줄여서, 그 코어를 화면에 돌려줍니다.
  - 페이지 획을 다시 만드는 스레드 수를 **절반**으로 줄입니다.
  - 타일 백그라운드 칠하기는 **한 번에 한 장**만 합니다.

### C. 축소했을 때는 덜 정밀하게 읽기
- 지금까지는 아무리 축소해도 획을 배율 100%용 정밀도로 만들었습니다. 이제 축소 배율에 맞춰 **50%, 25% 정밀도**로 페이지를 읽습니다. 화면에서 보이는 품질은 같고, 만들 점·삼각형 수가 줄어 페이지가 더 빨리 나타납니다.
- 확대하면 그만큼 다시 다듬습니다.
- 조금 축소할 때는 이미 더 정밀하게 만든 획을 **그대로 둡니다**. 지금까지는 배율이 한 단계만 바뀌어도 화면의 획을 전부 다시 만들었고, 다시 확대하면 또 만들었습니다. 이제 4배 넘게 더 정밀한 경우(크게 확대했다가 돌아온 경우)에만 메모리를 아끼려고 다시 만듭니다.

### F. 측정
- 진단 화면과 진단 내보내기에 다음 한 줄이 추가됩니다.
  - 최근 프레임의 **UI / sync / render / GPU 평균 시간**
  - 가장 느린 프레임의 각 시간
  - 늦은 프레임 수
  - 현재 GPU 타일 작업 비율, RenderThread가 밀리는 중인지
- 이 줄을 보면 끊김이 UI 쪽인지 RenderThread·GPU 쪽인지 바로 알 수 있습니다.

### E. 안티에일리어싱
- 품질은 그대로입니다. 0.99.6부터 그 비용을 RenderThread가 아닌 작업 스레드가 냅니다. 확대·축소 중에는 타일 그림을 부드럽게 늘려 보여 줍니다.
- 플랜의 "페이지 한 장 그림"은 넣지 않았습니다. 축소하면 512px 타일 몇 장이 페이지 전체를 덮기 때문에 따로 둘 이득이 작다고 봤습니다.

## 어떻게 확인했나
- 빌드, 네이티브 커널 점검, 전체 단위 테스트(142개 클래스)를 통과했습니다.
- 정밀도 단계, 다시 만들지 판단, 작업량 조절, 스레드 양보, 프레임 측정 요약에 테스트를 추가했습니다.

## 하지 않은 것 / 확인하지 못한 것
- **태블릿에서 돌려 보지 않았습니다.** fps 개선 정도는 숫자로 말할 수 없습니다.
- 축소해서 읽은 페이지를 다시 확대하면, 다시 다듬는 동안 잠깐 덜 선명할 수 있습니다.

## 태블릿에서 해 볼 것
1. 필기 많은 노트를 넘기며 3~5fps로 떨어지던 것이 나아졌는지.
2. 많이 축소한 상태에서 페이지를 빠르게 스크롤 → 페이지가 더 빨리 나타나는지.
3. 축소했다가 다시 확대 → 잠시 뒤 선명해지는지.
4. 렉이 남아 있으면 진단 → 내보내기에서 **"Frames (last …)" 줄과 "tiles painted off the render thread" 줄**을 보내 주세요. 다음 개선 방향을 이 숫자로 정합니다.
