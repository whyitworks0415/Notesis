> 수동 업데이트입니다. 앱이 먼저 알리지 않으며, **About · Help → Check for updates**에서 설치할 수 있습니다.

> ⚠️ 0.91.0부터 앱은 **Material 화면만** 씁니다. Liquid glass·Glassmorphism을 계속 쓰려면 0.90.28에 머무르세요.

요청하신 두 가지 큰 작업을 넣었습니다. **자체 GPU 잉크 렌더러(C++)**와 **C++로 읽는 메시 캐시(불러오기)**입니다. 기기에서 아직 확인하지 못해서 **실험 기능으로, 기본은 꺼져 있습니다.** 설정 → 진단 → **GPU 잉크 그리기 (실험)**에서 켭니다.

## 무엇을 하나
1. **메시 캐시 (C++ 불러오기)**
   - 페이지 획이 한 번 만들어지면, Ink가 만든 **실제 삼각형 그대로** 페이지 옆에 `<페이지>.mesh` 파일로 저장합니다. 이때 페이지 파일의 "도장"(수정 시각·크기)도 함께 적습니다.
   - 다음에 그 페이지가 화면에 들어오면, **Ink가 획을 다시 읽고 만들기 전에** C++가 캐시 파일을 바로 읽어 그 페이지를 그려 보여 줍니다. 진짜 필기가 준비되면 바꿔 끼웁니다.
   - 지금까지 쓰던 미리 저장한 그림(WebP)보다 지금 확대 배율에 맞게 선명합니다.
   - 페이지 파일이 바뀌어 도장이 맞지 않는 캐시는 쓰지 않습니다.
2. **GPU 잉크 렌더러 (C++ · OpenGL ES 3)**
   - 타일 하나에 들어가는 획 수천 개를 **정점 버퍼 하나로 묶어 그리기 호출 한 번**에 그립니다. 지금까지는 획마다 한 번씩 그렸습니다.
   - 앱 화면과 다른 자체 GL 컨텍스트에서, 작업 스레드가 그립니다.
   - 가장자리는 4배 멀티샘플링(MSAA)으로 부드럽게 합니다.
   - 결과는 하드웨어 버퍼에 바로 그려져 **복사 없이** 비트맵으로 화면에 넘어갑니다.
   - 캐시와 페이지 내용이 정확히 같을 때만 씁니다. 같은 글자 수정 횟수, 같은 획 모양, 저장 안 된 변경 없음이 조건이고, 아니면 지금까지 방식(0.99.6의 백그라운드 칠하기)으로 그립니다.

## 쓰지 않는 경우 (지금까지 방식으로 그림)
- 연필 흑연, 입자·점선 브러시, 형광펜, 반투명 색이 하나라도 있는 페이지. GPU 경로가 똑같이 그릴 수 없는 브러시입니다.
- 반투명 레이어가 있는 노트, 잠긴 노트, 올가미로 들어 올린 중인 획이 있는 타일.
- 확대·축소로 획 모양을 다시 다듬은 페이지. 다음에 불러올 때 캐시를 새로 만듭니다.
- GPU 오류가 3번 나면 그 실행 동안 자동으로 꺼집니다.

## 기술 정리
- **`ink_batch.cpp` (호스트에서 sanitizer 검사)**: 캐시 파일 읽기는 모든 길이·개수·색인을 경계 검사합니다. 무작위로 손상시킨 파일 2만 개로 메모리 오류가 없는지 확인했습니다. 타일 묶기는 먼저 개수를 센 뒤 한 번에 할당합니다.
- **`ink_gl.cpp`**: EGL 1×1 pbuffer와 ES 3.0 컨텍스트를 씁니다. AHardwareBuffer를 EGLImage로 연결한 텍스처를 4x MSAA 렌더버퍼에서 resolve하고, `glFinish` 뒤 `HardwareBuffer`로 넘깁니다.
- 캐시는 앱 백업 파일과 노트 이전 버전에 넣지 않습니다(획에서 다시 만들 수 있음). 페이지를 지우면 같이 지워집니다.
- 진단의 "tiles painted off the render thread" 줄에 **GPU 렌더러가 그린 타일 수**가, 진단 보고에 렌더러 상태가 나옵니다.

## 어떻게 확인했나
- 빌드, 축소(R8) 릴리스 빌드, Android 버전 검사(Lint), 전체 단위 테스트(146개 클래스)를 통과했습니다.
- 네이티브 점검에 새 C++ 검사를 추가해 통과했습니다: 캐시 왕복, 손상·잘림·도장 불일치 거부, 무작위 손상 2만 회, 타일 묶기.
- 캐시 파일 형식(Kotlin 쓰기 쪽)도 테스트했습니다.
- **호스트(PC) 측정**: 획 4,000개(정점 80만 개) 페이지 기준으로, 캐시 읽기 7~14ms, 타일 하나 묶기(획 719개) 0.6~1.2ms였습니다(실행마다 다름). 처음 짠 방식은 묶기에 39.8ms가 걸려서 방식을 고쳤습니다. **PC 수치이고 태블릿 수치가 아닙니다.**

## 하지 않은 것 / 확인하지 못한 것
- **태블릿에서 GPU 렌더러를 한 번도 돌려 보지 못했습니다.** 이 환경에는 GPU가 있는 Android 기기가 없습니다. 그래서 기본은 꺼 두었습니다.
- 켠 뒤 필기가 이상하게 보이거나 앱이 꺼지면 끄고 알려 주세요.
- 가장자리 부드럽게 처리가 Ink 자체 셰이더와 조금 다릅니다(MSAA). 아주 크게 확대하면 차이가 보일 수 있습니다.
- 저장되지 않은 변경이 있는 페이지와 확대 후 다시 다듬은 페이지는 GPU 경로를 쓰지 않습니다. 이것까지 쓰려면 캐시를 그때그때 다시 만드는 작업이 더 필요합니다.
- Google Ink의 C++ 엔진 자체를 앱에 넣는 방식은 쓰지 않았습니다. androidx.ink가 C++ API를 공개하지 않아서, 공개 API로 메시를 꺼내 저장하는 방식으로 대신했습니다.
- 메시 캐시만큼 저장 공간을 더 씁니다. 필기 많은 페이지는 수 MB일 수 있습니다.

## 태블릿에서 해 볼 것
1. 설정 → 진단 → **GPU 잉크 그리기 (실험)** 켜기 → "지금: 켜짐"인지 확인.
2. 필기 많은 노트를 열고 페이지를 끝까지 넘긴 뒤(캐시가 만들어짐) 노트를 닫았다가 다시 열기 → 페이지가 더 빨리, 선명하게 나타나는지.
3. 같은 페이지를 오가며 렉이 줄었는지, 필기 색·굵기·모양이 이전과 같은지.
4. 진단 → 내보내기에서 "by the GPU renderer" 숫자가 0보다 큰지, "GPU ink renderer: on"인지.
5. 이상하면 스위치를 끄고, 그 상황을 알려 주세요.
